## Understanding NoSQL Databases
### NoSQL Databases

- Over **80% of modern data is unstructured**, including text, images, social media posts, and logs.
- Traditional **SQL databases** use rigid, tabular structures that can struggle with the scale and variety of modern data.
- **NoSQL (Not Only SQL)** databases are designed to handle large volumes of structured and unstructured data.

> **Simply put:** NoSQL databases trade rigid structures for greater flexibility and scalability, making them useful when data is large, varied, or rapidly changing.

### Why Use NoSQL?

| Challenge | NoSQL Solution |
|---|---|
| Diverse/unstructured data | **Flexible schemas** |
| Rapidly growing datasets | **Horizontal scalability** |
| Large-scale applications | **High performance** |

### What Are NoSQL Databases?

- **NoSQL (Not Only SQL)** databases store data without relying solely on traditional relational tables.
- They can handle **structured, semi-structured, and unstructured data**.
- NoSQL databases are useful for **large, varied, and rapidly growing datasets** because they offer flexible schemas and easy scalability.

> **Simply put:** SQL works best when data fits a predictable structure, while NoSQL provides more flexibility when data varies or changes frequently.

### SQL vs NoSQL

| Feature | SQL | NoSQL |
|---|---|---|
| **Key focus** | Reducing data duplication | Scaling and rapid application change |
| **Storage model** | Tables with fixed rows and columns | Documents, key-value, wide-column or graph |
| **Schema** | Rigid/predefined | Flexible |
| **Object mapping** | Often requires ORM | Often maps more directly to application objects |
| **Scaling** | **Vertical** – larger/more powerful server | **Horizontal** – spread across multiple servers |

## Types of NoSQL Databases

### 4 Main Types

There are **four main types of NoSQL database**, each suited to different data needs:

| Type | How It Stores Data | Example | Common Use |
|---|---|---|---|
| **Document** | JSON-like documents containing fields and values | MongoDB | Blog posts, product catalogues |
| **Key-Value** | Each unique key maps to a value | Redis | Caching, sessions, shopping carts |
| **Wide-Column** | Data organised into flexible columns | Cassandra | Big data, analytics, call records |
| **Graph** | Nodes represent entities and edges represent relationships | Neo4j | Social networks, recommendations |

> **Simply put:** The best NoSQL type depends on the data. Documents suit flexible records, key-value stores favour speed and simplicity, wide-column databases handle large-scale datasets, and graph databases specialise in relationships.

#### Document Databases
- Store data as **JSON-like documents**.
- Documents can have different fields and structures.
- **MongoDB** is a common example.

#### Key-Value Stores
- Store data as simple **key → value** pairs.
- Very fast and simple to retrieve.
- **Redis** is commonly used for caching and session data.

#### Wide-Column Stores
- Organise data into **columns** rather than traditional fixed rows.
- Designed for querying and processing very large datasets.
- **Cassandra** is a common example.

#### Graph Databases
- Store **entities as nodes** and **relationships as edges**.
- Useful when relationships between data are particularly important.
- **Neo4j** is commonly used for social networks and recommendation systems.

## Discovering MongoDB

**MongoDB** is a popular **document-based NoSQL database** designed for handling large volumes of varied, semi-structured, and unstructured data.

#### Why MongoDB?

- **Flexible schema** – documents don't need identical structures.
- **Scalable** – designed to handle growing datasets.
- **Powerful querying** capabilities.
- Uses a **JSON-like document model**.
- Handles **unstructured and semi-structured data** effectively.

> **Simply put:** MongoDB is useful when your data doesn't fit neatly into fixed SQL tables or when its structure changes frequently.

### MongoDB Structure

| MongoDB | SQL Equivalent | Description |
|---|---|---|
| **Collection** | Table | Group of related documents |
| **Document** | Row | Individual data record containing field-value pairs |
| **Field** | Column | A piece of data within a document |

Unlike SQL tables, documents within the same collection **do not need to have the same schema**.

### Extracting Structured vs Unstructured Data

| Aspect | Structured Data | Unstructured Data |
|---|---|---|
| **Sources** | Relational databases, CSV files, Excel sheets | Web pages, logs, multimedia files, social media feeds |
| **Data retrieval** | SQL queries, database connectors | Web scraping, APIs, file parsers |
| **Complexity** | Depends on database schema and relationships | More challenging due to varied sources and lack of structure |
| **Tools & libraries** | SQL, JDBC/ODBC connectors, EL platforms | Beautiful Soup, multimedia and Machine Learning libraries |

### Transforming Structured vs Unstructured Data

Unstructured data requires more flexible transformation techniques because it can include **text, images, videos, and logs** without a predefined schema.

| Aspect | Structured Data | Unstructured Data |
|---|---|---|
| **Nature** | Relational, predefined schema | Text, images, videos, logs; no fixed schema |
| **Cleaning** | Handle missing values, duplicates and inconsistencies | Text: remove stop words/stemming; Images: resize/normalise |
| **Enrichment** | Derived columns and aggregates | Extract metadata, sentiment or image features |
| **Transformation** | Joins, filters and aggregations | Convert text/images into numerical representations |
| **Schema evolution** | Schema changes can be difficult | More flexible, but consistency can be challenging |
| **Complexity** | Complex with large relational datasets | Requires preprocessing before structured analysis |
| **Tools** | SQL, ETL tools, Apache Spark | NLTK, spaCy, OpenCV, TensorFlow |

> **Simply put:** Structured data can usually be transformed directly using SQL-style operations, while unstructured data often needs to be **cleaned and converted into a structured or numerical format first**.

## Unstructured Data from MongoDB to SQL

An **ETL pipeline** can transform flexible MongoDB data into structured SQL data for easier querying, reporting, and analysis.

> **Simply put:** Extract data from MongoDB, transform it into a structured format, then load it into SQL where it can be queried and used by analytics or BI tools.

### Transformation & Loading Challenges

| Challenge | Solution |
|---|---|
| **Data quality** – unstructured data can be messy | Clean data using tools such as **pandas** |
| **Computational intensity** – transformations can require significant resources | Use efficient algorithms or distributed processing |
| **Evolving data** – source structures may change | Regularly review transformation logic and use modular code |
| **Scalability** – data volumes increase | Use scalable databases or partitioning |
| **Data integrity** – data must remain accurate | Validate data before loading |
| **Performance** – queries can slow as data grows | Use indexes and optimise queries |

### Why Move MongoDB Data to SQL?

SQL databases provide:

- **Structured querying** for complex analysis.
- **Data integrity**, including ACID properties.
- Strong integration with **BI and reporting tools**.
- A more **stable and predictable schema**.

### MongoDB to SQL Process

1. **Evaluate** – map MongoDB collections/documents to a relational SQL structure.
2. **Transform** – flatten nested documents and normalise data into tables.
3. **Migrate** – transfer the transformed data into SQL.
4. **Validate** – check mappings, accuracy and ensure no data was lost.
5. **Optimise** – create indexes and optimise queries.
6. **Continuous sync** – if MongoDB continues receiving data, regularly transfer new data into SQL.

### Key Learning Points

- **NoSQL databases** handle unstructured and semi-structured data with flexible schemas and scalability. **MongoDB** is a popular document-based example.
- **ETL pipelines** can extract unstructured data through methods such as APIs and web scraping, then clean and transform it for analysis.
- Moving data from **MongoDB to SQL** enables structured querying, stronger data integrity, and easier analytics, but requires careful **transformation, validation, and optimisation**.
