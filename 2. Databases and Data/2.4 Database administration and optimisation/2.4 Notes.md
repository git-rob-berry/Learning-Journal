## Database Administration Best Practices
### Choosing the right Database Management System (DBMS)

- **Scalability** - Scalability refers to the ability to handle increasing data volumes and user loads
- **Performance** - Performance focuses on efficient query processing and response times
- **Data Consistency** - Data consistency ensures data integrity and consistency across the database
- **Transaction** - Transaction support handles concurrent transactions and maintains data consistency

- When choosing a **DBMS**, consider:
  - **Data structure and relationships**
  - **Data volume** and expected growth
  - **Query patterns** and performance needs
  - **Consistency vs availability** trade-offs

- The chosen DBMS should be supported by skilled **database administrators (DBAs)** who can:
  - Follow administration best practices
  - Optimise database performance
  - Troubleshoot issues

- When designing for **scalability and performance**, consider:
  - Data volume and growth rate
  - Query patterns and performance
  - **Partitioning and sharding**
  - **Caching**
  - Monitoring and performance tuning

- Plan for future data growth by considering:
  - Storage capacity and scalability
  - Data **archival and retention**

- Improve query performance by:
  - Identifying frequent and performance-critical queries
  - Using **indexing**
  - Applying **normalisation**
  - **Rewriting/optimising queries**
 
- Metrics
  - Query Performance - Poorly formatted or overly general queries can introduce slowdowns.
  - User & Query Conflicts - Slowdowns can occur when multiple users are accessing the database.
  - Business Transactions - Look at end-user experience of real-time performance.
  - Capacity - Be sure to change default settings for elements like buffer and query caches.
  - Configuration - Be sure to change default settings for elements like buffer and query caches.
 
- 6 Tips to Increase Database Performance
  1. Optimise Queries
  2. Improve Indexes
  3. Defragment Data
  4. Increase Memory
  5. Strengthen CPU
  6. Review Access

- **Partitioning and sharding** distribute data across multiple servers to improve **performance and scalability**:
  - **Horizontal partitioning (sharding)** – splits rows based on a key or range.
  - **Vertical partitioning** – splits data based on columns or data types.

- **Caching** reduces database load and improves response times:
  - Tools such as **Redis** or **Memcached**.
  - Frequently accessed data is stored in **memory** for faster retrieval.

- **Performance monitoring and tuning** involves:
  - Monitoring database metrics.
  - Identifying **bottlenecks and slow queries**.
  - Tuning database configurations.
  - Analysing and optimising **query execution plans**.

- **Data integrity and recovery**
  - Perform regular **backups**.
  - Test backup integrity and **restore procedures**.
  - Maintain a **disaster recovery plan** to minimise downtime and ensure availability.

- **Authorisation and access control**
  - Use secure user accounts and strong **authentication**.
  - Follow the **principle of least privilege** – users only get the access they need.
  - Use **Role-Based Access Control (RBAC)** to assign permissions based on roles and responsibilities.
  - Regularly review and update permissions.

- **Data encryption**
  - Encrypt sensitive data **at rest** and **in transit**.
  - Use strong encryption and secure **key management**.
  - Helps prevent **unauthorised access and data breaches**.
 
## SQL and NoSQL Databases

<br><br>

- Choosing between **SQL and NoSQL** depends mainly on the type of data and how it will be used.

| Database | Best suited for |
|---|---|
| **SQL** | Structured data with clear relationships and a fixed schema |
| **NoSQL** | Unstructured or semi-structured data requiring flexibility and scalability |

- **SQL** is like a **bus** – structured, organised and follows a defined route.
- **NoSQL** is like an **off-road vehicle** – flexible and able to handle varied data structures.
- A project containing both types may use **both SQL and NoSQL**, choosing each for the data it handles best.

- **SQL databases** enforce **ACID properties** to ensure reliable transactions:

| ACID | Meaning |
|---|---|
| **Atomicity** | Transaction completes fully or not at all |
| **Consistency** | Data remains valid and follows database rules |
| **Isolation** | Transactions don't interfere with each other |
| **Durability** | Committed changes are permanently saved |

- The key differences between **SQL and NoSQL** are their data models, scalability, query methods and consistency.

| Feature | **SQL** | **NoSQL** |
|---|---|---|
| **Data** | Structured | Unstructured or semi-structured |
| **Model** | Relational tables | Key-value, document, columnar or graph |
| **Schema** | Fixed, predefined | Flexible / schema-less |
| **Relationships** | Primary and foreign keys | Varies by database type |
| **Scalability** | Traditionally vertical | Designed for horizontal scaling |
| **Consistency** | Strong consistency / ACID | Often eventual consistency |
| **Querying** | Standardised SQL | Varies between databases |

- **SQL**
  - Uses **primary keys** to uniquely identify records and **foreign keys** to link tables.
  - Uses **normalisation** to reduce data redundancy and dependency.
  - Uses **Structured Query Language (SQL)**.
  - Common commands:
    - Definition: `CREATE`, `ALTER`, `DROP`
    - Manipulation: `SELECT`, `INSERT`, `UPDATE`, `DELETE`
  - Supports powerful **joins, aggregations and filtering**.

- **NoSQL**
  - Designed for large volumes of **unstructured and semi-structured data**.
  - Common models include:
    - **Key-value** – data stored as key-value pairs.
    - **Document** – documents such as JSON or XML.
    - **Columnar** – data organised by columns.
    - **Graph** – data represented as nodes and edges.
  - Uses a **flexible schema**, making changing data structures easier to handle.
  - Designed for **horizontal scaling** across multiple servers.
  - Optimised for high-volume **read and write operations**.
  - Often uses **eventual consistency**, prioritising availability and scalability while allowing temporary inconsistencies.
 
  - **SQL databases** are best suited for:
  - Structured and consistent data.
  - **Complex queries and transactions**.
  - Strong **data integrity and consistency**.
  - Examples: **financial systems, e-commerce platforms and content management systems**.

- **NoSQL databases** are best suited for:
  - Large volumes of **unstructured or semi-structured data**.
  - High **scalability and performance** requirements.
  - **Flexible and evolving schemas**.
  - Examples: **social networks, real-time analytics and content delivery networks**.
 
- **Database changes** can impact downstream systems, performance and costs.

- **Schema changes**
  - Adding or modifying columns in **SQL** may require updates to downstream applications.
  - **NoSQL** offers more flexibility for changing schemas.

- **Data format changes**
  - New data types or representations can affect **data pipelines**.
  - Data engineers should assess the impact and update affected processes.

- **Performance changes**
  - **Indexing and partitioning** changes can affect query speed and resource usage.
  - Monitor performance to ensure downstream systems are not negatively affected.

- **Processing and storage costs**

| | **SQL** | **NoSQL** |
|---|---|---|
| **Storage** | Often lower for structured data | Can be higher for unstructured/semi-structured data |
| **Processing** | Can be higher for complex joins and aggregations | Often efficient for simple queries and high-volume ingestion |

- Key factors affecting cost:
  - **Data volume** and growth.
  - Query **complexity and frequency**.
  - **Indexing and partitioning**.
  - Hardware and infrastructure.
  - **Licensing and support**.

## Monitoring and Optimising Database Performance

- Key **database monitoring metrics** help maintain performance, reliability and scalability.

| Metric | What it measures |
|---|---|
| **Response time** | How long queries take to execute and return results |
| **Throughput** | Number of queries/transactions processed over time |
| **Concurrency** | Number of simultaneous users or database connections |
| **Resource utilisation** | CPU, memory and disk I/O usage |
| **Indexing effectiveness** | How efficiently indexes support queries |

- Monitoring these metrics helps identify:
  - **Slow queries** and performance bottlenecks.
  - **Scaling requirements** as workloads increase.
  - Resource or **contention issues**.
  - High CPU, memory or disk usage.
  - **Missing or inefficient indexes**.

- Key **database monitoring metrics** help maintain performance, reliability and scalability.

| Metric | What it measures | Why it matters |
|---|---|---|
| **Response time** | Time taken to execute and return a query | Identifies **slow queries** affecting user experience |
| **Throughput** | Queries/transactions processed over time | Shows whether the database can **handle its workload** |
| **Concurrency** | Simultaneous users or database connections | Helps identify **contention** and capacity issues |
| **Resource utilisation** | CPU, memory and disk I/O usage | Identifies **resource bottlenecks** and inefficient queries |
| **Indexing effectiveness** | How efficiently indexes support queries | Helps find **missing or inefficient indexes** and improve query speed |

- Together, these metrics help identify **performance problems, scaling needs and optimisation opportunities**.

- **Database monitoring tools** track performance, query execution and resource usage.

- Most DBMSs include **built-in monitoring tools**, for example:
  - **Oracle Enterprise Manager**
  - **SQL Server Management Studio (SSMS)**
  - **MySQL Workbench**

- **Third-party monitoring tools** can provide additional:
  - Performance monitoring
  - Automated **alerts**
  - Reporting and dashboards
  - Resource and query analysis

- These tools help identify **slow queries, bottlenecks and resource issues** before they significantly affect performance.

### Database Performance Optimisation

- **Query profiling**
  - Analyses executed queries and their **performance metrics**.
  - Identifies **slow queries, inefficient patterns and bottlenecks**.
  - Improvements may include **rewriting queries or restructuring tables**.
  - Regular reviews help monitor database health and guide optimisation decisions.

- **Indexing strategies**
  - Create indexes on **frequently queried columns**.
  - Choose index types based on the **data and query patterns**.
  - Monitor indexes to identify **unused or inefficient indexes**.

- **Database configuration**
  - Tune settings such as **memory, buffers, caching and parallelism**.
  - **Horizontal scaling (sharding)** – distributes data across multiple servers to spread workload and improve scalability.
  - **Vertical scaling** – adds more CPU, memory or storage to a single server.
  - Monitor resources to prevent **capacity saturation**.

- **Collaboration**
  - **Data engineers** focus on pipelines, integration and data architecture.
  - **DBAs** focus on database management, performance and security.
  - Both should collaborate on **database design, schema changes, migrations and performance optimisation**.
  - Regular knowledge sharing and performance reviews improve overall database management.
 
### How to Optimise Your Database

- **Indexing**
  - Indexes speed up data retrieval by reducing **disk I/O**.
  - Prioritise columns that are **frequently queried** or have **high cardinality**.
  - Avoid unnecessary indexes, as they consume storage and can slow `INSERT`, `UPDATE` and `DELETE` operations.
  - Monitor index usage and use the index type best suited to the query and data.

- **Manage database size**
  - Avoid unnecessary database growth to reduce **storage and I/O overhead**.
  - Regularly monitor and manage **index and file fragmentation**.
  - Archive or remove data that is no longer required.

- **Optimise tables**
  - Keep table structures efficient and avoid unnecessarily large tables.
  - Where appropriate, **partition large tables** to improve manageability and query performance.
  - Reuse existing structures rather than creating unnecessary tables or indexes.

- **Reduce resource usage**
  - Optimise **CPU, memory and storage** requirements.
  - Review database configuration and storage requirements regularly.
  - The goal is to maintain performance while reducing unnecessary infrastructure costs.

- **Remove unnecessary data**
  - Use `TRUNCATE TABLE` when you need to efficiently remove **all rows** from a table.
  - Reducing unnecessary data can decrease storage requirements and improve performance.

- **Use auto-incrementing IDs**
  - Auto-incrementing **primary keys** give each row a unique identifier.
  - This simplifies record identification and prevents duplicate IDs.

- **Enable statistics**
  - Database statistics help the **query optimiser** choose efficient execution plans.
  - Keep statistics **accurate and up to date** to maintain query performance.

### Case study: HR database optimisation

- **Background**
  - HR database stores **employee, payroll and performance data**.
  - Growing data volumes caused **slow queries and high CPU usage**.
  - Analysis identified **complex joins and poor indexing** as key issues.

- **Action**
  - Applied optimisation techniques including:
    - **Denormalisation**
    - **Indexing**
    - **Sharding**
  - Monitored and tuned the **database configuration**.

- **Outcome**
  - Faster **query response times** and better resource utilisation.
  - Improved **data retrieval and reporting**.
  - Better integration with other HR systems.
  - **DBAs** play an important role in keeping SQL and NoSQL databases optimised and efficient.

## Summary 

- **Key learning points**
  - Choose the right **DBMS** based on scalability, performance, consistency and transaction requirements.
  - Understand when to use **SQL vs NoSQL**.
  - Design for scalability using **partitioning, sharding and caching**.
  - Protect data using **access controls, authentication, RBAC, encryption, patching and backups**.
  - Monitor **response time, throughput, concurrency, resource usage and indexing**.
  - Improve performance through **query optimisation, indexing, configuration tuning and scaling**.
  - Encourage collaboration between **data engineers and DBAs**.
  - Apply these techniques to maintain **reliable, scalable and high-performing databases**.
